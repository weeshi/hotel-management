Repository Layer (Data Access)

External Services & Queue
Gateways (7) + Bull + Redis
🔌 خدمات خارجية + طابور غير متزامن7 بوابات دفع، بريد إلكتروني، SMS. Bull + Redis للمهام غير المتزامنة: إيميلات، إشعارات، شحنات مجدولة.
🗄️ PostgreSQL (مع Decimal/Enums/Json)  |  ⚡ Redis (Cache/Queue)
📦 البنية التحتيةPostgreSQL قاعدة البيانات الرئيسية مع Decimal للحسابات المالية، Enums للحالات، Json للقواعد. Redis للتخزين المؤقت و Bull Queue للمهام غير المتزامنة.

لماذا PostgreSQL + Redis؟

اختيارنا لـ PostgreSQL يأتي لمتطلبات نظام فندقي دقيق:

  • Decimal للحسابات المالية — دقة كاملة بدون أخطاء تقريب Float
  • Enums للحالات — BookingStatus, PaymentMethod, FolioStatus — تكامل على مستوى قاعدة البيانات
  • Json/JsonB للقواعد المرنة — سياسات الإلغاء، إعدادات الفندق، أيام التطبيق
  • Redis للتخزين المؤقت + Bull Queue للمهام غير المتزامنة

02

🏰 الهندسة السحابية والاستمرارية — SaaS الحقيقي

كيف تتغلب كبرى الشركات (Netflix, Salesforce) على التحديات التشغيلية؟ العلامة البيضاء، الكتلة السحابية، العقدة المحلية، وخطة التعافي من الكوارث.

العلامة البيضاء ودومين خاص لكل فندق (White-label + IP Masking)

  • كل فندق يحصل على دومين خاص به: booking.alsalam-hotel.ly
  • الزائر والهاكر يرون عنوان الفندق فقط — لا أحد يعرف أين يقع سيرفر المنصة
  • شهادة SSL مجانية وتلقائية لكل دومين عبر Cloudflare
  • هوية العلامة التجارية للفندق كاملة: شعار، ألوان، رسائل
  • النظام لا يعرف الفندق إلا من النطاق نفسه (customDomain فريد لكل فندق بمطابقة تامة — exact match)
  • قفل على مستوى الفندق: من يسجّل الدخول عبر دومين فندق معيّن يعمل لذلك الفندق فقط، حتى لو أُدخلت بيانات حساب فندق آخر
  • عزل تلقائي عبر الكوكيز (Host-only cookies بدون Domain attribute) — لا حاجة لأي إعداد إضافي
🌐 booking.alsalam-hotel.ly 🛡️ Cloudflare (الدرع) ☁️ السيرفر المخفي
الـ IP الحقيقي مخفي تمامًا خلف Cloudflare — مستحيل استهداف السيرفر مباشرة
تم تنفيذه بالكامل في v3.5 — النظام يثق بالدومين فقط خلف Cloudflare (cf-ray) أو TRUST_PROXY=true، وروابط الدعوة تُبنى على نطاق المنصة (تعمل حتى أثناء انتشار DNS)

ليس سيرفرًا واحدًا — كتلة سحابية (Cloud Cluster)

نحن لا نشتري "كمبيوتر" ونضع فيه الفنادق! النظام وقاعدة البيانات يعملان ككتلة سحابية (Cluster):

Auto-scaling

  • عند زيادة الضغط ← السحابة تستنسخ السيرفر تلقائيًا إلى 2 و 3 لتقاسم الحمل
  • عند الهدوء ← تعود تلقائيًا إلى الحجم الطبيعي
  • لا يوجد "نقطة فشل واحدة" (No Single Point of Failure)

Master-Replica

  • قاعدة بيانات أساسية (Master) + "ظل" (Replica) ينسخ البيانات في نفس اللحظة
  • عطل الأساسية ← الظل يستلم العمل في أجزاء من الثانية دون أن يشعر الفندق
  • الانهيار الكلي شبه مستحيل تقنيًا

العقدة المحلية = Micro-PMS (وليس النظام الكامل)

رفضنا تركيب "النظام الكامل" في العقدة المحلية — لأننا نعود لعيوب أنظمة المداد القديمة (بطء، صيانة مكلفة، تحديثات معقدة). نثبّت نسخة طوارئ مصغّرة للخط الأمامي فقط.

✅ يفعله Micro-PMS❌ لا يفعله
تسكين (Check-in)تقارير الإدارة العليا
مغادرة (Check-out)إعدادات النظام العميقة
إضافة رسوم على الفاتورةإدارة الأسعار والقنوات
طباعة الفواتيربوابات الدفع المتقدمة
  • ينهار السيرفر في أمريكا أو ينقطع الإنترنت في ليبيا؟ الاستقبال لا يتوقف ثانية واحدة
  • بعد إصلاح السيرفر ← العقدة تصبّ بياناتها الجديدة في السحابة بهدوء (مزامنة آمنة)
  • متكاملة مع بروتوكولات العمل بدون إنترنت: Heartbeat + 4G + Allotment
التوازن: خفة النظام + استمرارية التشغيل

خطة التعافي من الكوارث — 3 سيناريوهات

أ) عطل تقني احتمال 5%

عطل جهاز أو انهيار برمجي (تحديث خاطئ):

  • الحل: Infrastructure as Code (IaC)
  • إعادة بناء سيرفر مطابق في 15 دقيقة بضغطة زر
  • مثال: احترق سيرفر لندن ← بناء مطابق في ألمانيا

ب) هجوم DDoS وارد جدًا

إغراق السيرفر بطلبات وهمية:

  • الحل: Cloudflare WAF
  • يمتص مليارات الطلبات الوهمية قبل وصولها للسيرفر
  • إسقاط السيرفر بهذه الطريقة شبه مستحيل

ج) اختراق / Ransomware احتمال ضعيف

سرقة بيانات أو تشفيرها:

  • Row-level Isolation: الهاكر حتى لو سرق حساب فندق، لا يرى بقية الفنادق
  • PITR: نسخة احتياطية مستمرة لحظية
  • مسح في 3:00 ← إرجاع لحالة 2:59 وكأن شيئًا لم يكن

👑 لماذا هذه العمارة هي الأفضل؟

في أسوأ سيناريو كارثي يمكن تخيله (السيرفر الرئيسي انهار بالكامل، والنسخة الاحتياطية تحتاج ساعتين للعودة): موظفو الفنادق لن يصابوا بالذعر — لأن العقدة المحلية في كل فندق مستمرة في العمل واستقبال النزلاء، مما يمنح فريقنا التقني الوقت الكافي لإصلاح السحابة دون أن يفقد الفندق دولارًا واحدًا من إيراداته.

هذه هي هندسة الـ SaaS الحقيقية التي تُباع بملايين الدولارات

35+ نموذج Prisma مع PostgreSQL — تستخدم Decimal للحسابات المالية، Enums للحالات، Json للقواعد المرنة.

النماذج الأساسية والفندق

  • Hotel — إعدادات الفندق، العملة (LYD)، أوقات الدخول/الخروج، المنطقة الزمنية Asia/Tripoli، settings (Json)
  • User — 7 أدوار مع 2FA، قفل حساب، تتبع آخر دخول
  • RefreshToken — تدوير آمن مع عائلة (Replacement Detection)
  • Guest — الضيوف مع تحقق الإيميل، نقاط الولاء
  • RoomType — أنواع الغرف + baseRate (Decimal) + capacity + صور
  • RoomTypeExtraBed — أسرّة إضافية لكل نوع غرفة (price Decimal)
  • RoomTypeDefaultService — خدمات افتراضية لكل نوع غرفة
  • RoomTypeAmenity — مرافق لكل نوع غرفة
  • Room — غرف فردية + حالة نظافة + حالة تشغيل (RoomStatus Enum)

الأسعار والحجوزات والخدمات

  • RatePlan — أسعار موسمية مع nightlyRate (Decimal), minStay, maxAdults/Children, extraBedPrice, applyDays (Json)
  • CancellationPolicy — قواعد إلغاء مرنة (Json rules)
  • ServiceCategory — فئات الخدمات
  • Service — خدمات فردية مع price (Decimal) + ربط ضريبي
  • TaxRule — ضرائب متعددة (VAT, سياحية, بلدية) مع rate (Decimal)
  • Booking — رقم تسلسلي، حالة (BookingStatus Enum)، مصدر (BookingSource Enum)
  • BookingRoom — حجوزات متعددة الغرف + ربط بـ RatePlan + nightlyRate (Decimal)
  • BookingService — خدمات مرتبطة بالحجز مع price (Decimal)

الفوترة والمدفوعات

  • Folio — حساب الغرفة مع totalCharges/totalPaid/balance (Decimal), status (FolioStatus Enum)
  • FolioTransaction — حركة مالية مع amount/taxAmount/taxableAmount (Decimal)
  • ScheduledCharge — شحنات مجدولة (إيجار ليلي تلقائي) مع amount (Decimal)
  • RoomCharge — شحن الإيجار الليلي لكل غرفة مع amount/taxAmount (Decimal)
  • FolioDiscount — خصومات (نسبة أو مبلغ) مع value/amount (Decimal)
  • Payment — amount (Decimal), method (PaymentMethod Enum), status (PaymentStatus Enum)
  • Refund — استرداد كامل وجزئي مع amount (Decimal)
  • Invoice — فواتير مع رقم تسلسلي ورابط PDF

الوحدات الإضافية

  • Wallet — محفظة إلكترونية للضيف مع balance (Decimal), unique (guestId, hotelId)
  • WalletTransaction — حركات المحفظة مع amount (Decimal), idempotencyKey
  • MenuCategory — فئات قائمة الطعام
  • MenuItem — أصناف الطعام والشراب مع price (Decimal)
  • RestaurantOrder — طلبات المطعم مع totalAmount (Decimal), status, orderNo
  • RestaurantOrderItem — بنود الطلب مع quantity, price (Decimal)
  • SafeDepositBox — صناديق الأمانات مع حالة وتوقيع الموظف
  • SafeDepositBoxItem — أصناف داخل الصندوق
  • LostItem — المفقودات مع صورة، حالة، بيانات المستلم

التدبير والصيانة

  • TaskType — أنواع المهام (تنظيف، صيانة كهرباء، سباكة، دهان...) مع أيقونة وترتيب
  • HousekeepingTask — مهام التدبير مع priority (HIGH/NORMAL/LOW), assignedTo, status
ملاحظة مهام الصيانة تستخدم نفس النظام مع taskType مختلف وأولوية خاصة

الإشعارات والشركاء والتقارير

  • AuditLog — سجل تدقيق كامل: user, action, entity, entityId, oldValue, newValue, ip, userAgent

  • ReportSetting — إعدادات التقارير: logoUrl, headerText, footerText, taxNumber

🔐 المصادقة والأمان — 7 طبقات + 7 أدوار

نظام أمني متكامل مع مصادقة متعددة العوامل (JWT + 2FA)، صلاحيات دقيقة (RBAC)، وتدقيق كامل (Audit Log).

طبقات الأمان السبعة

الطبقة 1 النقل: HTTPS + HSTS + Helmet.js
الطبقة 2 المصادقة: JWT (Access 15min + Refresh 7days مع Rotation) + 2FA (TOTP)
الطبقة 3 الصلاحيات: RBAC مع 7 أدوار + Permission Check لكل نقطة وصول
الطبقة 4 حماية: CSRF (Double-submit cookie) + Rate Limiting (100 req/min/IP) + Zod Validation
الطبقة 5 المراقبة: Audit Log + قفل الحساب (5 محاولات فاشلة ← lock 15 دقيقة)
الطبقة 6 الشركاء: API Key + HMAC Signature + IP Whitelist + Rate Limit مخصص
الطبقة 7 الجلسات: Refresh Token Rotation + كشف سرقة التوكن (إلغاء عائلة التوكن عند إعادة استخدام ملغي)

استراتيجية Refresh Token Rotation

🔹 Access Token: 15 دقيقة فقط

🏨 الوحدات الأساسية — الفندق، الغرف، الحجوزات، الأسعار

اللبنة الأساسية للنظام: إدارة الفنادق، الغرف، الأسعار الموسمية، سياسات الإلغاء، والحجوزات مع دعم كامل للتعددية.

إدارة الفندق والغرف

  • Hotel — معلومات الفندق، العملة (LYD الافتراضية)، أوقات الدخول/الخروج، المنطقة الزمنية Asia/Tripoli
  • RoomType — أنواع الغرف مع baseRate (Decimal), capacity, صور، مرافق
  • RoomTypeExtraBed — أسرّة إضافية مع سعر منفصل وحد أقصى للعدد
  • RoomTypeDefaultService — خدمات مضمنة مع نوع الغرفة (مجانية أو مدفوعة)
  • RoomTypeAmenity — مرافق ووسائل راحة لكل نوع غرفة
  • Room — غرف فردية بحالتين: حالة تشغيلية (Available/Occupied/Maintenance) وحالة نظافة (Clean/Dirty)
  • تقويم شهري ملون يعرض توفر الغرف (متاح/مشغول/صيانة/قيد التنظيف)

الأسعار الموسمية (Rate Plans)

  • خطط أسعار ديناميكية تغطي فترات متعددة (صيف، رمضان، عيد، عطلات)
  • سعر ليلي (nightlyRate) من نوع Decimal — دقة مالية كاملة
  • دعم minStay (الحد الأدنى لليالي)، maxAdults، maxChildren
  • سعر سرير إضافي منفصل (extraBedPrice)
  • أيام التطبيق (applyDays كـ Json): [0,1,2,3,4,5,6]
  • ربط كل خطة بسياسة إلغاء مختلفة (Flexible/Moderate/Strict)
  • إمكانية تفعيل/تعطيل الخطة (isActive)

سياسات الإلغاء

نظام قواعد Json مرن يدعم مستويات متعددة غير محدودة:

مرنة إلغاء مجاني قبل 48 ساعة من الدخول
معتدلة استرداد 50% قبل 24 ساعة
صارمة لا استرداد بعد تأكيد الحجز
مخصصة قواعد Json مرنة لأي سيناريو (Non-refundable, partial حسب تاريخ الإلغاء)

الحجوزات

  • حجوزات متعددة الغرف عبر BookingRoom — غرفتين أو أكثر بفاتورة موحدة
  • أرقام تسلسلية (bookingNo) فريدة
  • مصادر متعددة: Website, Reception, Partner (BookingSource Enum)
  • حالات: PENDING → CONFIRMED → CHECKED_IN → CHECKED_OUT → CANCELLED / NO_SHOW
  • خدمات مرتبطة بالحجز (أثناء الحجز أو أثناء الإقامة)
  • إلغاء مع استرداد تلقائي (كامل/جزئي حسب سياسة الإلغاء المرتبطة)
  • حقول للضيوف غير المسجلين: guestName, guestEmail, guestPhone

معادلات الفوترة (PostgreSQL Decimal)

// معادلات حساب الفاتورة (Decimal)
totalRoomCharges = Σ nightlyRate × nights × rooms
totalServiceCharges = Σ (service.price × qty)
subtotal = totalRoomCharges + totalServiceCharges
discountAmount = (type=PERCENTAGE) ? subtotal × value/100 : value
totalTax = Σ (taxRule.rate × taxableAmount) // Json tax breakdown
totalCharges = subtotal − discountAmount + totalTax
balance = totalCharges − totalPaid

💰 المحفظة الإلكترونية (Wallet)

محفظة رقمية لكل ضيف لكل فندق — تتيح إيداع وسحب الرصيد، مع تسوية تلقائية مع فاتورة الفندق (Folio).

نموذج المحفظة

  • Wallet — لكل ضيف محفظة مرتبطة بالفندق (unique constraint: guestId + hotelId)
  • WalletTransaction — سجل حركات المحفظة مع balance (Decimal) و idempotencyKey (لمنع مضاعفة الحركات)
  • أنواع الحركات: DEPOSIT (إيداع), WITHDRAW (سحب), PAYMENT (دفع), REFUND (استرداد)
  • طرق الإيداع: كاش، تحويل بنكي، من محفظة أخرى، استرداد من فاتورة
  • إيصال PDF للمحفظة عبر wallet-receipt-pdf.service.ts

التكامل مع Folio

  • تسوية تلقائية: يمكن استخدام رصيد المحفظة لتسديد فاتورة الفندق عند Check-out
  • إنشاء FolioTransaction تلقائياً عند الخصم من المحفظة
  • إشعار للضيف عند كل حركة (إيداع/سحب)
  • صلاحيات: Admin/Manager/Reception يديرون المحفظة، Guest يرى محفظته فقط
  • خيار إعادة الرصيد المتبقي نقداً عند المغادرة

سير عمل المحفظة

إيداع نقدي تسجيل في Wallet إضافة رصيد (Decimal) استخدام للدفع تسوية Folio إيصال PDF

🍽️ المطعم والخدمات الإضافية

مطعم (POS)، صناديق الأمانات، المفقودات والمعثورات، التدبير المنزلي والصيانة — وحدات متكاملة ضمن النظام الموحد.

نظام المطعم (Restaurant POS)

  • MenuCategory — فئات القائمة (مشروبات، مقبلات، رئيسية، حلويات) مع ترتيب وأيقونة
  • MenuItem — أصناف الطعام مع price (Decimal)، صورة، وصف
  • RestaurantOrder — طلبات المطعم مع رقم طلب تسلسلي، حالة (PENDING, PREPARING, SERVED, PAID)
  • RestaurantOrderItem — بنود الطلب مع quantity, price (Decimal), ملاحظات
  • أنواع الطلبات: DINE_IN (داخلي), ROOM_SERVICE (غرفة), TAKEAWAY (خارجي)
  • ربط الطلب بحجز الفندق (bookingId) لترحيل التكلفة إلى Folio
  • إمكانية تحويل فاتورة المطعم مباشرة إلى فاتورة الغرفة
  • واجهة Reception + Admin + Restaurant لإدارة الطلبات

صناديق الأمانات (Safe Deposit Box)

  • SafeDepositBox — لكل غرفة، مع حالة (ACTIVE/CLOSED), توقيع الموظف الفاتح والمغلق
  • SafeDepositBoxItem — أصناف داخل الصندوق مع وصف وعدد
  • سير عمل: فتح الصندوق ← تسجيل الأصناف ← إغلاق عند المغادرة ← توقيع إلكتروني
  • صلاحية: Reception + Admin فقط

المفقودات والمعثورات (Lost & Found)

  • LostItem — وصف القطعة، مكان العثور، صورة (imageUrl)، حالة (PENDING/RETURNED)
  • بيانات المستلم: الاسم، رقم الهوية، تاريخ الاستلام
  • تسجيل من قبل أي موظف (HK, Maintenance, Reception, Restaurant)
  • لوحة عرض وتصفية وبحث في Admin و Reception

التدبير المنزلي (Housekeeping)

  • TaskType — أنواع المهام (تنظيف عام، تنظيف عميق، تعقيم، ترتيب السرير...) مع أيقونة
  • HousekeepingTask — مهام مع priority (HIGH/NORMAL/LOW), تعيين موظف, حالة
  • حالات الغرفة: CLEAN → DIRTY (بعد الخروج) → IN_PROGRESS → INSPECTED → CLEAN
  • جدولة تلقائية: عند Check-out ← حالة الغرفة DIRTY ← إنشاء مهمة تنظيف
  • صلاحية: Housekeeping (تنفيذ), Admin (إدارة)

الصيانة (Maintenance)

  • يستخدم نفس HousekeepingTask لكن مع TaskType مختلف (كهرباء، سباكة، تكييف، دهان...)
  • أولوية خاصة: HIGH (عاجل) — استجابة فورية
  • إمكانية إرفاق ملاحظات وصور للعطل
  • تعيين لفني الصيانة المختص
  • جدولة صيانة دورية (يومية/أسبوعية/شهرية)
  • صلاحية: Maintenance (تنفيذ), Reception (إبلاغ), Admin (إدارة)

📨 الإشعارات والتواصل — Queue-based

نظام إشعارات غير متزامن عبر Bull + Redis — يدعم إيميلات (Resend/SendGrid) و SMS مع إعادة محاولة تلقائية.

البنية التحتية للإشعارات

  • Bull Queue + Redis — طابور مهام غير متزامن
  • إعادة محاولة تلقائية: 3 محاولات مع فاصل زمني متزايد
  • تصنيف الإشعارات حسب النوع: Email, SMS, Push
  • تسجيل حالة كل إشعار: PENDING, SENT, FAILED
  • إمكانية إعادة إرسال الإشعارات الفاشلة يدوياً

أنواع الإشعارات

  • تأكيد الحجز — فوري بعد الدفع، مع ملخص الحجز ورابط PDF
  • تذكير 24 ساعة — قبل موعد الدخول: "غداً موعد وصولك في فندقنا"

  • إشعار الإلغاء — عند إلغاء الحجز مع تفاصيل الاسترداد

  • SMS — إشعارات عاجلة (اختياري، حسب مزود الخدمة)

🔌 API الشركاء والتقارير

واجهة برمجة تطبيقات موثقة للشركاء الخارجيين (Booking.com, Expedia)، مع نظام تقارير شامل وتحكم كامل.

Partner API

  • ApiPartner — إدارة الشركاء مع apiKey (فريد), apiSecret, allowedIPs (IP Whitelist)
  • WebhookEndpoint — نقاط Webhook مع تحديد الأحداث المسموح بها
  • Rate Limit مخصص لكل شريك (rateLimit + dailyLimit)
  • HMAC Signature للتحقق من هوية الطلبات
  • توثيق OpenAPI 3.0 كامل (docs/api/openapi.yaml)
  • Channel Manager — الربط مع منصات الحجز: Booking.com, Expedia, Airbnb
  • API endpoints: الحجوزات، الغرف، الأسعار، التوفر، التقارير

التقارير والإحصائيات

  • Occupancy Rate = (ليالٍ مشغولة ÷ إجمالي الليالي المتاحة) × 100
  • ADR (Average Daily Rate) = إيراد الغرف ÷ ليالٍ مشغولة
  • RevPAR (Revenue Per Available Room) = إيراد الغرف ÷ إجمالي الغرف المتاحة
  • GOPPAR (Gross Operating Profit Per Available Room) — متقدم
  • Pickup Report — تتبع الحجوزات القادمة
  • Forecast — توقعات الإشغال والإيرادات
  • تصفية حسب: اليوم، الأسبوع، الشهر، السنة، نطاق زمني مخصص
  • ReportSetting — تخصيص التقارير: شعار الفندق، ترويسة، تذييل، رقم ضريبي

سجل التدقيق (Audit Log)

تتبع كل عملية حساسة في النظام مع 6 أبعاد: من (user)، متى (timestamp)، إيش (action)، على إيش (entity + entityId)، من وين (IP + userAgent)، التغيير (oldValue → newValue).

مثال: Admin@2026-06-15 14:30 ← غيّر سعر الغرفة 201 من 450.00 إلى 550.00 مثال: Reception@2026-06-15 15:00 ← سجّل دخول الضيف أحمد (Booking #B-0001)

السوق الليبي — الفرصة الحقيقية

+1,500 فندق وشقة فندقية (تقدير)

📶 بروتوكولات العمل بدون إنترنت

ثلاثة بروتوكولات متكاملة تضمن استمرار تشغيل الفندق حتى عند انقطاع الإنترنت — بلا توقف، بلا Overbooking، وبلا فقدان بيانات.

Smart Time-Scoped Auto-Stop Heartbeat

النظام يرسل نبضة (Heartbeat) كل 30 ثانية من جهاز الاستقبال إلى الخادم:

  • عند انقطاع الاتصال — العمليات الحساسة (الدفع، Check-out) تتحول تلقائيًا لوضع مؤجّل
  • العمليات الآمنة (شحن ليلي، حجوزات محلية) تُصفّر في طابور محلي (OfflineSyncQueue)
  • سجل Heartbeat يحفظ آخر اتصال + حالة كل جهاز (آمن / منقطع)
  • عودة الاتصال ← مزامنة آمنة مع كشف التعارضات قبل الدمج

IoT / 4G Telemetry Fallback شريحة طوارئ

كل جهاز استقبال مزوّد بشريحة 4G احتياطية:

  • عند فشل الإنترنت الأساسي ← إعادة توجيه تلقائية إلى شبكة 4G خلال ثوانٍ
  • بدون أي تدخل من الموظف — التشغيل مستمر دون أن يشعر أحد
  • مثالي للمناطق التي يتذبذب فيها الإنترنت
  • تنبيه للمسؤول عند تكرار استخدام الشريحة الاحتياطية

Allotment Strategy حصص معزولة

تخصيص حصص معزولة (Allotment) للقنوات الإلكترونية:

  • عدد محدود من الغرف يُعرض على Booking.com / Expedia — والباقي محجوز للاستقبال المباشر
  • عند الانقطاع ← الحصص المجمّدة لا يمكن حجزها إلكترونيًا (منع Overbooking)
  • الاستقبال المحلي يستمر بالبيع بشكل طبيعي داخل الحصص المخصصة
  • عودة الاتصال ← مزامنة الحصص مع القنوات تلقائيًا

تدفق الانقطاع الكامل

عميل يدفع Heartbeat يكتشف الانقطاع الطلب في الطابور المحلي عودة الاتصال مزامنة آمنة + إيصال
النتيجة: صفر فقدان بيانات، صفر Overbooking، صفر توقف تشغيلي — تُبنى فوق العقدة المحلية Micro-PMS

التطوير التقني — 4 مراحل منتج

بُنية المنتج تُطوَّر على 4 مراحل متتالية — كل مرحلة تنتج وحدة تشغيلية كاملة قبل الانتقال للتالية:

1) Housekeeping

التدبير المنزلي: الغرف، حالات النظافة، المهام، الجدولة — أول وحدة تشغيلية ملموسة.

2) Pricing / CRM

الأسعار الديناميكية + ملفات الضيوف والولاء — تحويل البيانات إلى قرارات تسعير.

3) Booking Engine

محرك الحجز الفوري + الدفع الإلكتروني — يفتح قناة البيع المباشر.

4) Channel Manager

الربط مع Booking.com و Expedia و Airbnb — بيع الغرفة من كل القنوات بدون Overbooking.
